0. Sənəd haqqında
Bu sənəd Kampus tələbə cüzdanının MVP-sini 7 gündə qurmaq üçün yeganə mənbədir. Backend, mobil və admin komandası, həmçinin Claude Code eyni sənəddən işləyir.
Oxucular: backend (Spring Boot), mobil (React Native), admin (Next.js) developerləri və Claude Code.
Konvensiyalar
Mətn Azərbaycan dilindədir; API, DB, kod və identifikatorlar ingilis dilindədir.
[REAL]: tam işləyən funksiya, real məntiq və real data axını ilə.
[MOCK]: xarici sistemin simulyasiyası; interfeysi real sistemlə eynidir, sonradan əvəz edilə bilər.
Mütləq: demo üçün vacibdir. Arzuolunan: vaxt qalarsa.
Hüquqi istinadlar Mərkəzi Bankın qaydalarına edilir (bölmə 10).

1. Məhsul icmalı
Kampus tələbələr üçün rəqəmsal cüzdandır: ödəniş, köçürmə, virtual kart və mikrokredit bir tətbiqdə. Əsas fərq: gündəlik ödəniş sadədir, təhlükəsizlik yalnız risk olanda işə düşür.
Problem
Tələbələrin çoxunun rəsmi gəliri və öz bank kartı yoxdur; banklar onları kredit üçün rədd edir.
Yadda saxlanmış kartla abunəlik fırıldaqları real itkiyə səbəb olur (komanda üzvünün 400 AZN itkisi).
Dostlar arasında hesab bölmək, pul istəmək nağd pul və ya kart nömrəsi ilə edilir.
Hədəf auditoriya
Əsas: 18+ yaşlı universitet tələbələri.
Sonra (roadmap): 16–17 yaşlılar, valideyn razılığı ilə Teen hesab.
İkinci tərəf: kampus ətrafındakı kafe, mağaza, kitab satıcıları (QR ilə ödəniş qəbulu).
Dəyər təklifi
2 dəqiqəyə məsafədən hesab və virtual kart, bank filialına getmədən.
Satıcıya kilidli və limitli virtual kartlar: abunəlik fırıldağı keçmir.
Telefon nömrəsi ilə P2P, hesabı bölmə, pul istəmə.
50 AZN-dək "Sonra ödə" və partnyor kreditorlardan təkliflər.
Tələbə üçün pulsuz; gəlir satıcılardan və partnyorlardan gəlir.
m10-dan fərq: m10 hamı üçün cüzdandır; Kampus tələbənin maliyyə həyatı üçün qurulub və onu fırıldaqdan qoruyur.

2. Arxitektura
Kampus bir Spring Boot monolitidir, daxildə aydın sərhədli modullara bölünür. Xarici sistemlər (bank, AniPay, kart şəbəkəsi, VASP, BOKT, dövlət reyestri, SİMA) ayrıca kampus-sim servisində simulyasiya olunur. Beləliklə real inteqrasiya sərhədi kodda görünür və mock sonradan real API ilə əvəz edilə bilər.

API konvensiyaları

GMA istisnaları (risk əsaslı autentifikasiya)
Fraud modulu hər əməliyyat üçün REQUIRE_SCA və ya EXEMPT qərarı verir:
Kiçik məbləğ (GMA 3.9): ≤60 AZN, son GMA-dan sonra ardıcıl ≤5 əməliyyat və cəmi ≤300 AZN → istisna.
Etibar edilən şəxs (GMA 3.6, 3.7): alan siyahıdadırsa → istisna; siyahıya əlavə etmək GMA tələb edir.
Öz hesabları arasında (GMA 3.8): istisna.
TRA (GMA 3.10, 4.2): fraud dərəcəsi həddən aşağıdırsa və risk siqnalı yoxdursa → istisna.
Digər hallar: GMA tələb olunur.
İstisna olduqda belə qeydiyyatlı cihazda tətbiqin açıq sessiyası tələb olunur (GMA 3.13).
Etibarlılıq və data bütövlüyü
Idempotency: Idempotency-Key + (user_id, key) unikal indeksi; təkrar sorğu ilk cavabı qaytarır (24 saat saxlanılır).
Race condition: balans dəyişən əməliyyatlarda hesablar SELECT ... FOR UPDATE ilə, həmişə account_id artan sırası ilə kilidlənir (deadlock qarşısı).
Outbox: heç bir hadisə itmir; worker hər 500 ms-də emal edir, uğursuzluqda eksponensial təkrar cəhd.
Saga: çoxaddımlı axınlarda (kart köçürməsi, kripto ödəniş) hər addımın kompensasiyası var.
Audit və loqlar
Hər pul hərəkəti, GMA qərarı, admin əməliyyatı və feature flag dəyişikliyi audit_log cədvəlinə yazılır (kim, nə, nə vaxt, IP, cihaz).
Audit qeydləri dəyişdirilmir və silinmir (yalnız INSERT).
Strukturlaşdırılmış JSON loqlar, hər sorğuda traceId.
Performans (demo hədəfləri)
Ödəniş və köçürmə API-ləri: p95 < 300 ms (mock gecikmələri xaric).
Kart avtorizasiyası (mock): < 150 ms qərar.
Admin monitorinq: hadisədən ekrana < 1 saniyə (WebSocket).
Fərdi məlumatlar
Hər data paylaşımı üçün ayrıca razılıq qeydi (consents cədvəli: növ, versiya, tarix); kredit partnyoruna data yalnız razılıqla gedir.
eKYC şəkil və videoları ayrıca, şifrələnmiş saxlanılır (demo: lokal disk, AES-256).

Balans və HOLD
ledger_balance: bütün yazılışların cəmi.
held_amount: aktiv HOLD-ların cəmi (kart köçürməsi, kart avtorizasiyası, kripto ödənişi gözləyərkən).
available_balance = ledger_balance − held_amount. İstifadəçiyə bu göstərilir və xərc limiti də buna görə yoxlanılır.
HOLD statusları: ACTIVE → CAPTURED | RELEASED | EXPIRED (default müddət 15 dəqiqə).
İnvariantlar
Hər journal_entry üçün: cəmi debet = cəmi kredit.
Qoruma invariantı: CUSTOMER_FUNDS_BANK balansı = bütün USER_WALLET + MERCHANT_WALLET balanslarının cəmi.
Heç bir USER_WALLET mənfiyə düşə bilməz ("Sonra ödə" ayrıca CREDIT_RECEIVABLE hesabından keçir).
Yazılışlar dəyişdirilmir; səhv yalnız əks yazılışla (reversal) düzəldilir.
Gündəlik üzləşdirmə (Qayda 7.4–7.5)
Hər gün 00:05-də (demoda düymə ilə) ReconciliationJob işə düşür:
kampus-sim-dən partnyor bankın mock çıxarışını alır.
Çıxarışdakı qalığı CUSTOMER_FUNDS_BANK ledger balansı ilə müqayisə edir.
Qoruma invariantını yoxlayır.
Nəticəni reconciliation_runs cədvəlinə yazır: MATCHED və ya MISMATCH + fərq.
Admin paneldə göstərilir: "Ledger ↔ bank: uyğundur".

5. Modullar
Hər modul eyni struktura malikdir: məqsəd, istifadəçi hekayələri, ekranlar, API, DB, biznes qaydaları və qəbul meyarları. Qəbul meyarları demoda yoxlanılan ssenarilərdir.
5.1 Qeydiyyat və eKYC
Yeni istifadəçi 2–3 dəqiqəyə filiala getmədən hesab açır. Axın Mərkəzi Bankın "Məsafədən hesabların açılması Qaydası"na (44/5) uyğundur: real liveness, dövlət bazası ilə üz tutuşdurması (mock) və SİMA İmza ilə müqavilə (mock).
İstifadəçi hekayələri
Tələbə kimi telefonumla, ŞV-mlə və selfie ilə hesab açmaq istəyirəm ki, banka getməyim.
Kampus kimi 18 yaşdan kiçik şəxsin hesab açmasının qarşısını almaq istəyirəm.
Compliance əməkdaşı kimi hər qeydiyyatın liveness nəticəsini və imzalanmış müqaviləni görmək istəyirəm.

5.2 Autentifikasiya və GMA
Giriş və hər pul hərəkəti bir mərkəzi qərar xidmətindən keçir: ScaDecisionService. O, əməliyyatın GMA tələb edib-etmədiyini bölmə 3-dəki qaydalara görə müəyyən edir və qərarı audit-ə yazır.
İstifadəçi hekayələri
Tələbə kimi 15 AZN-lik kafe ödənişində yalnız tətbiqi açmaq və təsdiqləmək istəyirəm.
Tələbə kimi böyük və ya yeni alana köçürmədə Face ID ilə təsdiq etmək istəyirəm.
Tələbə kimi tez-tez pul göndərdiyim dostları "etibar edilən" siyahısına əlavə etmək istəyirəm.
Giriş (challenge-response)
Mobil GET /auth/challenge ilə nonce alır.
İstifadəçi Face ID və ya PIN ilə cihaz açarını açır və nonce-u imzalayır.
POST /auth/login → access token (JWT, 5 dəq) + refresh token (30 gün, cihaza bağlı).
Tətbiq 5 dəqiqə aktivsiz qalarsa, kilid ekranı çıxır (GMA 2.2.5).
Əməliyyatın təsdiqi
Biznes modulu (məsələn, transfers) ScaDecisionService.decide(ctx) çağırır.
Cavab EXEMPT(reason) olarsa, əməliyyat dərhal icra olunur.
Cavab REQUIRE_SCA olarsa, əməliyyat PENDING_SCA statusunda saxlanılır və mobilə challenge qaytarılır: {txId, nonce, amount, payee}.
Mobil təsdiq ekranında məbləği və alanı göstərir, Face ID tələb edir və sign(txId|amount|payee|nonce) imzasını göndərir.
Server imzanı cihazın açıq açarı ilə yoxlayır → əməliyyat icra olunur. Challenge-in müddəti 2 dəqiqədir.
Qərar konteksti
record ScaContext(UUID userId, UUID deviceId, String operationType,                  long amountMinor, String payeeRef, boolean payeeTrusted,                  boolean ownAccounts, RiskSignals signals) {}sealed interface ScaDecision {  record Exempt(ExemptionReason reason) implements ScaDecision {}   // LOW_VALUE, TRUSTED, OWN_ACCOUNTS, TRA  record Require(String challengeId) implements ScaDecision {}}
Kiçik məbləğ istisnası üçün sayğaclar Redis-dədir: sca:{userId}:count və sca:{userId}:sum. Hər uğurlu GMA-dan sonra sıfırlanır.
Uğursuz cəhdlər və yeni cihaz
PIN və ya imza 3 dəfə ardıcıl səhv olarsa → hesab 30 dəqiqəlik bloklanır, istifadəçiyə bildiriş gedir (GMA 2.2.3).
Yeni cihazdan giriş: OTP + PIN + təkrar liveness (5.1-dəki 3 hərəkət).
Yeni cihazda ilk 24 saat: 200 AZN-dən böyük köçürmələr 30 dəqiqəlik gözləməyə düşür (fraud siqnalı, 5.8).

5.5 P2P köçürmə, pul istə və hesabı böl
Tələbə telefon nömrəsi ilə pul göndərir: alan Kampus istifadəçisidirsə köçürmə daxili və anidir, deyilsə partnyor bank vasitəsilə AniPay-ə gedir. Pul istə və hesabı böl eyni köçürmə mexanizmi üzərində qurulub.
İstifadəçi hekayələri
Tələbə kimi dostuma telefon nömrəsi ilə 2 toxunuşda pul göndərmək istəyirəm.
Tələbə kimi göndərməzdən əvvəl alanın adını görmək istəyirəm ki, səhv adama getməsin.
Tələbə kimi 60 AZN-lik kafe hesabını 4 dosta bölüb kimin ödədiyini izləmək istəyirəm.
Tələbə kimi səhv göndərdiyim köçürməni 5 saniyə ərzində ləğv etmək istəyirəm.
Alanın müəyyən edilməsi
Kontaktlar: telefon nömrələri cihazda normallaşdırılır (+994XXXXXXXXX), SHA-256 hash ilə serverə göndərilir. Server Kampus istifadəçilərini qaytarır. Açıq nömrələr serverə getmir.
Nömrə daxil edildikdə: GET /transfers/resolve?phone=...
Kampus istifadəçisi → INTERNAL, maskalanmış ad ("Sərxan B.").
Kampusda deyil → sim-in AniPay kataloqu → ANIPAY, bankın adı + maskalanmış ad.
Heç yerdə tapılmadı → "Bu nömrə AniPay-də qeydiyyatda deyil, kart nömrəsi ilə göndərin" (5.6).
Köçürmə axını
Məbləğ, qeyd (emoji ilə), təsdiq ekranı (alanın maskalanmış adı ilə).
POST /transfers → ScaDecisionService (etibar edilən şəxs, kiçik məbləğ və s.).
Köçürmə SCHEDULED statusu ilə yaradılır, execute_at = now + 5 san. Ekranda "Ləğv et" geri sayımı.
5 saniyə bitəndə worker icra edir:
INTERNAL: D USER_WALLET(A) / C USER_WALLET(B) → COMPLETED; B-yə push.
ANIPAY: D USER_WALLET(A) / C ANIPAY_SETTLEMENT → sim-ə göndərilir → PENDING. Sim 2–10 saniyədə webhook ilə SETTLED və ya REJECTED qaytarır. Rədd → əks yazılış, istifadəçiyə bildiriş.
Gələn AniPay köçürməsi (sim webhook): D CUSTOMER_FUNDS_BANK / C USER_WALLET.
Pul istə
İstifadəçi bir və ya bir neçə Kampus istifadəçisindən məbləğ və qeydlə pul istəyir.
Alan "Gələn sorğular" bölməsində görür: "Ödə" (adi köçürmə axını) və ya "İmtina et".
Sorğunun müddəti 7 gündür; 24 saatdan bir xatırlatma push-u (maks. 2).
Hesabı böl
Başlanğıc: uğurlu QR ödənişindən ("Hesabı böl" düyməsi) və ya əl ilə məbləğ daxil edərək.
İştirakçıları seç; bölgü bərabər (qalıq qəpik təşkilatçıya düşür) və ya fərdi məbləğlərlə.
Hər iştirakçıya bağlı pul istə sorğusu yaradılır (split_id).
Təşkilatçının ekranında irəliləyiş: "3/4 ödəyib · 45.00 / 60.00 AZN".

5.6 Kart nömrəsinə köçürmə
Tələbə istənilən Azərbaycan bankının kartına kart nömrəsi ilə pul göndərir. Kart nömrəsi (PAN) heç vaxt Kampus serverinə gəlmir: o, sim-in təhlükəsiz formasında daxil edilir və Kampus yalnız token alır. Pul əvvəl dondurulur (HOLD), kart şəbəkəsi təsdiq edəndən sonra tutulur (CAPTURE).
İstifadəçi hekayələri
Tələbə kimi anamın kartına nömrə ilə pul göndərmək istəyirəm.
Tələbə kimi kart nömrəsini yazanda hansı banka getdiyini görmək istəyirəm.
Tələbə kimi balansımı öz kartıma çıxarmaq istəyirəm.
Axın
Məbləğ daxil edilir, mövcud balans və komissiya göstərilir.
Kart: saxlanmış alan kartı seçilir və ya "Yeni kart" → sim-in təhlükəsiz forması (WebView).
Forma daxilində: Luhn yoxlaması (səhv nömrə dərhal qırmızı), BIN üzrə bankın adı və loqosu.
Forma Kampusa yalnız {cardToken, bin, last4, bankName, brand} qaytarır.
POST /card-transfers → ScaDecisionService → lazım olarsa Face ID.
LedgerService.placeHold(...) → status HELD.
kampus-sim kart şəbəkəsinə OCT göndərilir → status SENT.
Sim 1–3 saniyədə cavab verir:
APPROVED → captureHold: D USER_WALLET / C CARD_SETTLEMENT + komissiya D USER_WALLET / C FEE_INCOME → COMPLETED.
DECLINED → releaseHold → FAILED, səbəb istifadəçiyə göstərilir.
60 saniyədə cavab gəlməzsə → sim-dən status sorğusu; yenə bilinməzsə → UNDER_REVIEW və admin növbəsi.

Sim-dən gələn təkrarlanan (merchant-initiated) ödənişlər satıcıya görə qruplaşdırılır: satıcı, son çıxılma, tipik məbləğ, növbəti gözlənilən tarix və "Blokla" düyməsi. Bloklama həmin satıcını kartın qara siyahısına əlavə edir.
"Bu mən deyiləm"
Hər kart əməliyyatı bildirişində düymə var. Basıldıqda kart dərhal dondurulur və disputes qeydi açılır (status OPEN). Admin fraud növbəsində görür; mock chargeback ilə məbləğ geri qaytarıla bilər.

Fraud dərəcəsi (GMA 4.4)
fraud_rate = rüb ərzində fırıldaq kimi təsdiqlənmiş əməliyyatların həcmi / həmin növ əməliyyatların ümumi həcmi. Hər əməliyyat növü üzrə ayrıca hesablanır; GMA-sız keçən əməliyyatlar da daxildir. Demo üçün həm rüblük, həm də "son 7 gün" göstərilir.
Xəbərdarlıq ekranı (WARN)
"Diqqət: fırıldaqçılar tez-tez uduş, depozit və ya kredit vəd edərək pul istəyir. Bu şəxsi şəxsən tanıyırsınız?" Düymələr: "Tanıyıram, davam et" (sonra Face ID) və "Ləğv et".
Fraud növbəsi (admin)
HOLD_FOR_REVIEW halları burada görünür: istifadəçi, məbləğ, alan, tetiklənən qaydalar, bal. Admin "Təsdiqlə" (HOLD capture olunur) və ya "Rədd et" (HOLD açılır, istifadəçiyə bildiriş) seçir. Cavab gözləmə müddəti 30 dəqiqə; vaxt bitərsə avtomatik rədd.
Texniki tələblər
Hər qayda FraudRule interfeysini implement edən Spring bean-dir: RuleResult evaluate(FraudContext ctx).
Sayğaclar Redis-də (sürüşən pəncərə): fraud:{userId}:out:10m, fraud:{recipientId}:senders:24h.
Qiymətləndirmə < 30 ms.
Hər qiymətləndirmə fraud_evaluations-a yazılır (audit və fraud dərəcəsi üçün).

5.9 Kredit: "Sonra ödə" və partnyor marketplace
Kredit modulunun iki hissəsi var. "Sonra ödə" Kampusun öz mikrokreditidir: 50 AZN-dək, 2 ayadək, yalnız öz kapitalı hesabına (Qayda 9). Bundan böyük kreditləri partnyor BOKT və banklar verir; Kampus yalnız ərizəni və (razılıqla) scoring datasını ötürür. Hər iki hissə yalnız 18+ istifadəçilər üçündür.
A. "Sonra ödə" (≤50 AZN)
İstifadəçi hekayəsi: tələbə kimi balansım çatmayanda kafedə 12 AZN-i indi ödəyib sonra qaytarmaq istəyirəm.
Uyğunluq (Kampus siyasəti)
KYC tamamlanıb, yaş ≥ 18, hesab ≥ 14 gündür açıqdır.
Son 30 gündə ən azı 2 top-up və ya gələn köçürmə.
Gecikmiş "Sonra ödə" borcu yoxdur.
Harada istifadə olunur: QR ödənişində ödəniş mənbəyi kimi və virtual kartda "balans çatmayanda Sonra ödə" seçimi aktivdirsə. Kredit yalnız ödəniş əməliyyatı üçün verilir (Qayda 9.1).

7. Xarici sistem mockları (kampus-sim)
kampus-sim real tərəfdaşların davranışını təqlid edən ayrıca Spring Boot servisidir. Kampus onunla real inteqrasiya kimi danışır: HTTP sorğular, gecikmələr, asinxron webhook-lar və uğursuzluqlar. Hər mockun "uğursuzluq rejimi" var ki, demoda xəta ssenariləri göstərilsin.
Ümumi qaydalar
Kampus → sim: REST, X-Api-Key başlığı.
Sim → Kampus: webhook, X-Sim-Signature (HMAC-SHA256, ortaq açar).
Hər mockun gecikməsi və uğursuzluq ehtimalı /sim/admin səhifəsindən dəyişdirilir.
Sim-in öz UI səhifələri (sadə HTML) demoda "xarici dünya" rolunu oynayır.

9. İş bölgüsü və 7 günlük plan
Backend, mobil və admin paralel işləyir; Gün 6-nın sonunda kod donur və Gün 7 yalnız məşq və deploy yoxlaması üçündür.

7 günlük plan · 3 xətt, 1 donma nöqtəsi
Mobil və admin backend hazır olana qədər OpenAPI əsasında mock server ilə işləyir, beləliklə heç bir xətt digərini gözləmir.
İş qaydaları
Gün 1: bütün API-lər üçün openapi.yaml yazılır (bölmə 5-dəki cədvəllərdən). Bu, üç xətt arasında müqavilədir.
Prioritet: əvvəl demo ssenarisindəki (bölmə 8) ulduzsuz addımlar, sonra ulduzlu addımlar, sonra "Arzuolunan" funksiyalar.
Gündəlik: 15 dəqiqəlik sinxronizasiya; bloklanan məsələ dərhal yazılır.
Claude Code: hər modul üçün docs/spec/ qovluğundakı uyğun Markdown faylı tapşırıq kimi verilir; qəbul meyarları testlərə çevrilir.
Gün 6: kod donur, ehtiyat demo videosu yazılır. Bundan sonra yalnız kritik xətalar düzəldilir.
Gün 7: make demo-reset + tam demo 3 dəfə, vaxt ölçülür.
